# ADR 0006:肤质分类从 4 型升级为 16 型四维度(每维度独立置信度)

- **状态:** 已采纳
- **日期:** 2026-07-04

## 背景

初版契约(需求文档 4.5 / ADR 0001)用单枚举 `skinType`(干性 / 油性 / 混合性 / 敏感性)+ 一个全局 `confidence`。

后续拿到用户真实的 16 型肌肤护理手册数据(`docs/raw-data/history_skin-info/history_skin_info_structured.json`),其分类体系是 **4 个二元维度组合**(2^4 = 16 型),且每型自带护理思路 / 产品搭配 / 注意事项。它与"4 型粗分"不是同一套东西。

单枚举的两个硬伤:

- 表达不了"偏油、但敏感判不准"这类**分维度**判定;全局一个 confidence 也压不住"哪一维不确定"。
- 敏感程度本质是肌肤反应性 / 耐受度,**单张照片只拍到此刻**,判定本就不稳。需要一种诚实表达不确定性的方式 —— 而不是给用户加一道问卷。

## 决策

契约从单枚举升级为**结构化四维度** `skinAxes`,四维各为二元:

| 维度 | 字段 | 取值 |
| --- | --- | --- |
| 油脂分泌 | `oilDry` | O 油 / D 干 |
| 敏感程度 | `sensitivity` | S 敏感 / R 耐受 |
| 痘痘情况 | `acne` | A 有痘 / F 无痘 |
| 色沉情况 | `pigment` | P 有色沉 / N 无色沉 |

- **每维度自带 `confidence`**(取代旧的全局 confidence),维度值用 `enum` 卡死。
- 后端从四维**派生** `skinTypeCode`(如 `O-S-F-P`)与 `skinTypeName`(如 油敏色皮)写入契约,**两端直接渲染,不各自维护 16 型对照表**。
- `zones` / `suggestions` / `disclaimer` 保留;`zones`(部位问题点)与 16 型(整脸分型)**正交互补**。

## 理由

- **贴合真实数据**:16 型直接对上用户手册;`suggestions` 可按判定型号取该型护理思路。
- **诚实降级敏感维度**:每维度独立置信度,是"敏感低置信 + 前端标『参考』"的前提 —— 用**透明置信度替代敏感问卷**,零交互成本,且不夸大"AI 能精确测敏感",合规站得住。
- **防漂移**:code / name 后端一处派生,避免 uniapp(TS)与 flutter(Dart)各写一份 16 型映射 —— 延续 ADR 0001 的 SSOT 精神。
- **继续约束 LLM**:维度值 enum 卡死,千问VL 结构化输出照样有 schema 兜底。

备选:**16 枚举平铺**(`skinType` 直接列 16 个值)。否决 —— 平铺值承载不了分维度置信度,做不出"偏向程度"的分维度 UI,也对不上科普页逐维度讲解。

## 后果

- ➕ 表达力强(分维度判定 + 置信度)、贴合真实数据、敏感维度可诚实降级、code/name 防漂移。
- ➖ schema 变长(四维各内联 enum + confidence);后端需实现"四维 → code/name"派生 + 16 型映射表(收在后端一处)。
- ➖ **需求文档 4.5 的旧契约示例与新 schema 不一致** —— 本 ADR 取代其字段结构;W1 落地时同步该示例或标注"以 `shared/skin-report.schema.json` 为准"。
- ⚠️ 产品搭配里的**具体产品(品牌 / 品名)不进 MVP 契约**,`suggestions` 只到成分 / 品类层 —— 合规 + 留 V2。
- 取代 ADR 0001 列举的字段结构(skinType / 全局 confidence);SSOT 与两端类型生成机制(0001)不变。
